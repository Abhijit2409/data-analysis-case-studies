# Methodology decision log

Every analytical choice, with the evidence behind it and what it would cost if
it turned out to be wrong.

**Status of everything below: PROPOSED, not approved.** No cleaning has been
applied. The audit counted problems; it did not fix them.

Two rules for reading this file:

- A threshold is only listed if there is a reason for it from **this** dataset. A
  number that is merely conventional is marked as such, because a convention is
  not evidence.
- "May change after Phase 2" means the decision depends on something not yet
  measured.

## Part A: decisions already taken in Phase 1

### D-01 Keep the raw timestamp text, not just the parsed value

| | |
|---|---|
| **Question** | How should timestamps be read? |
| **Decision** | Load `Date_time` as text, keep it, and parse a UTC copy alongside it. |
| **Evidence** | The raw text carries the UTC offset, e.g. `2014-01-01T01:00:00+01:00`. Parsing straight to UTC discards the offset, which is the only evidence of how the clock change was handled. |
| **Alternative rejected** | Parsing directly to UTC, as the OpenOA loader does. It is correct for its purpose but would have hidden the clock-change defect found in D-02. |
| **Limitation** | Slightly more memory. Immaterial at this size. |
| **May change** | No. |

### D-02 Treat the clock-change records as a known defect, not as random loss

| | |
|---|---|
| **Question** | Why does each turbine have exactly 12 duplicated and 12 absent timestamps? |
| **Decision** | Record them as a systematic clock-change defect, and investigate rather than assume the cause. That investigation became D-05. |
| **Evidence** | Every duplicate falls on a spring clock-change date (2014-03-30, 2015-03-29); every absent interval on an autumn one (2014-10-26, 2015-10-25). Neither is random. |
| **Alternative rejected** | Keeping the first of each duplicate pair. The two versions disagree by a median of 127 kW and up to 828 kW, so the choice would change the result arbitrarily. |
| **Limitation** | 48 duplicated and 48 absent records, 0.0228% of rows. Trivial in volume — but treating it as a small local defect would have missed D-05. |
| **May change** | No. |

### D-05 The summer timestamps are wrong by one hour across the whole dataset

| | |
|---|---|
| **Question** | Is the clock-change defect confined to those days, or a symptom of something larger? |
| **Decision** | Treat the summer offset as **incorrect**. No join between SCADA and any other time series may be made until it is corrected. |
| **Evidence** | Every local day has exactly 144 records, including both clock-change days, which a daylight-saving-aware logger cannot produce. **Test A:** on 2014-03-30 both copies of the duplicated hour are continuous with real data — one follows the 01:50 record, the other leads into 04:00 — so the logger never skipped an hour. **Test B:** comparing the daily temperature cycle against ERA5, which is independent and stored in UTC, the best lag is −1 h in winter and −2 h in summer, a difference of exactly one hour. Both tests point the same way: the logger clock never moved, and `+02:00` was written on top of unchanged local time. |
| **Alternative rejected** | Trusting the offsets because the timestamps are timezone-aware. That is precisely what makes this defect dangerous — it looks correct. Also rejected: cross-checking against `plant_data`, which cannot settle it because it was built from the same timestamps. |
| **Limitation** | The direction is inferred from the mechanism, and the correction is a proposal (P-11), not yet applied. The tests establish that summer and winter are misaligned by one hour; they do not independently prove which season is right. |
| **Affects** | Any join to reanalysis, including air density (P-09), and any reasoning by time of day. **Does not affect** the power curve or energy totals, because wind and power sit in the same row and move together. |
| **May change** | No on the finding. Yes on the correction rule. |

### D-03 Do not use the meter series to validate SCADA

| | |
|---|---|
| **Question** | Can turbine output be reconciled against metered export, the strongest available credibility check? |
| **Decision** | **No.** Drop the meter reconciliation from the project. |
| **Evidence** | The OpenOA loader states the meter was *"generated by adding artificial electrical loss and uncertaitny to SCADA data"*. Measured directly: the meter-to-turbine-sum ratio averages 0.980 with a standard deviation of 0.008, and the two correlate at 0.9997. Real metering does not track SCADA that closely. |
| **Alternative rejected** | Using it anyway and calling it a reconciliation. That would be presenting a derived series as independent evidence. |
| **Limitation** | **This removes the single best external check on the analysis.** It must be stated plainly in the final write-up, not buried. |
| **May change** | No. |

### D-04 Do not use `availability_kwh` or `curtailment_kwh` as ground truth

| | |
|---|---|
| **Question** | Can these fields label real availability or curtailment events? |
| **Decision** | No. Use them only as a cross-check on internal consistency. |
| **Evidence** | The loader states they were *"generated by estimating availability and curtailment from SCADA data"*. Measured: `availability_kwh` is non-zero in 3,842 intervals, and 3,074 of those (80%) are intervals where a turbine sat idle in usable wind — close tracking of a SCADA-derived rule. `curtailment_kwh` is non-zero in only 40 intervals (0.04%). |
| **Alternative rejected** | Training or validating against these as labels. It would be circular: the model would be scored against a rule derived from the same data. |
| **Limitation** | Leaves the project with **no labelled events of any kind**. |
| **May change** | No. |

## Part B: proposed cleaning rules, awaiting approval

### P-01 Valid wind-speed range

| | |
|---|---|
| **Proposed** | Accept 0–30 m/s. Exclude nothing on wind speed alone. |
| **Evidence** | Measured range is 0.00 to 19.31 m/s. **Zero records fall outside 0–30.** The rule excludes nothing here, so it is a guard for reruns rather than a filter. |
| **Alternative** | A tighter cap such as 25 m/s. Rejected: it would exclude real high-wind operation and no evidence supports it. |
| **Limitation** | A stuck sensor can report a plausible value, so this check cannot catch every sensor fault. P-04 covers that. |
| **May change** | No. |

### P-02 Valid power range

| | |
|---|---|
| **Proposed** | Flag power above 2,255 kW (rated + 10%) as invalid. Keep negative power down to −50 kW as valid idle consumption. Flag below −50 kW. |
| **Evidence** | Rated is 2,050 kW from the asset table. Measured maximum is 2,051.87 kW, so **no record exceeds rated by more than 0.1%**. Measured minimum is −17.92 kW, so **no record falls below −50 kW**. 77,431 records (18.4%) sit in the small-negative band, which is normal: a turbine that is not generating still draws power for its own systems. |
| **Alternative** | Treating all negative power as invalid. Rejected: it would discard 18.4% of rows that are physically correct and are exactly the idle periods the analysis is about. |
| **Limitation** | The ±10% tolerance is conventional, not derived. It happens to exclude nothing here. |
| **May change** | No. |

### P-03 Duplicate handling

| | |
|---|---|
| **Proposed** | Exclude the 96 records that make up the 48 duplicated pairs, from both the reference subset and the scoring period. Report them separately. The 48 absent intervals cannot be excluded — they are already missing — so record them as unmeasured time. |
| **Evidence** | Per D-02, the paired values disagree materially. Test A (D-05) shows both copies are genuine data with the label wrong, so neither is the "bad" one to drop. |
| **Alternative** | Averaging the pair — rejected, it fabricates a value never recorded. Re-timing the pairs using Test A's continuity logic — deferred to P-11, because it should be part of one consistent re-timing rule rather than a special case. |
| **Limitation** | Removes 0.02% of rows. Negligible for energy; must still be disclosed. |
| **May change** | Yes, if P-11 is approved, these records can be re-timed instead of dropped. |

### P-11 Correcting the summer one-hour shift

| | |
|---|---|
| **Proposed** | Rebuild the UTC timestamp by treating every record's wall-clock value as a fixed UTC+1 logger clock, ignoring the written offset. Keep the original column alongside so the change is auditable and reversible. |
| **Evidence** | D-05. The logger clock did not follow daylight saving, so a fixed offset reproduces real time; the written offset does not. |
| **Alternative** | Leaving the data as-is and avoiding all cross-series joins. Rejected: it would rule out air-density normalisation (P-09), which is needed for a fair model comparison. Also rejected: correcting only the summer months, which would introduce a discontinuity at each transition. |
| **Limitation** | **This is the single highest-risk proposed rule.** It rests on an inferred mechanism, not on documentation from the data publisher. It must be validated before use: after re-timing, the seasonal lag difference against ERA5 should fall to zero. If it does not, the rule is wrong and must be withdrawn. |
| **May change** | Yes — it is a hypothesis with a defined test. |

### P-04 Stuck sensor rule

| | |
|---|---|
| **Proposed** | Flag wind-speed readings inside a run of 6 or more identical consecutive values. Do **not** apply the same rule to power. |
| **Evidence** | Six records is one hour. Real wind varies at 10-minute resolution, so an hour of an identical reading to 2 decimal places indicates a frozen sensor. This flags 933, 1,209, 1,447 and 1,020 records per turbine (0.9%–1.4%). The longest run is 42 records (7 hours). Power is excluded from the rule because a stopped turbine legitimately reports a constant value for long stretches. |
| **Alternative** | A 3-record threshold. Rejected as too aggressive: short flat runs do occur in light, steady wind. A 12-record threshold would miss the shorter freezes. |
| **Limitation** | **6 is a judgement, not a measurement.** Phase 2 should test 3 and 12 as a sensitivity and report whether the conclusion moves. |
| **Also measured** | Of 4,609 frozen records, 4,608 have power still moving while only the wind reading is stuck, and 1 has both frozen. So these are stuck anemometers, not repeated rows. That is the more damaging kind: the turbine behaves normally while the x-axis of the power curve is wrong. |
| **May change** | Yes, pending that sensitivity test. |

### P-05 Missing timestamps and missing values

| | |
|---|---|
| **Proposed** | Never fill a gap with zero. Keep three separate categories: *absent interval*, *present but no value*, and *present with a zero value*. Exclude the first two from both the reference subset and the loss calculation, and report the excluded volume. |
| **Evidence** | Gaps are clustered, not scattered: 2,569 missing values fall in 65 runs, the longest being 132.8 hours on R80721. 388 gaps are moments when **no turbine reported at all**, which points at the data link rather than the turbines. Only 47 to 821 gaps per turbine are unique to that turbine. |
| **Alternative** | Treating a gap as zero production. Rejected: it would invent downtime. On R80721 it would manufacture more than five days of false outage. |
| **Limitation** | Excluding gaps means the estimate covers only observed time. Any loss during a data outage is **unmeasured, not zero**, and the final number must say so. |
| **May change** | No. |

### P-06 Zero-power observations

| | |
|---|---|
| **Proposed** | Keep them. Do not exclude. Classify separately as *idle in low wind* (below 4 m/s) and *idle in usable wind* (4 m/s and above). |
| **Evidence** | 3,824 records (0.91%) show no power with wind at 4 m/s or more. These are the analytical target of the whole project, not noise. Of those, 3,626 occurred while at least one other turbine was producing, and 198 while none were. |
| **Alternative** | Dropping zero-power rows before fitting. Rejected: it would delete the phenomenon being studied. |
| **Limitation** | Two, both material. **First**, the 4 m/s threshold is above the nominal cut-in for this turbine class and chosen to be conservative, but it is **not** measured from the data; Phase 2 should derive the actual cut-in empirically. **Second**, the 3,824 count uses each turbine's *own* anemometer — including while that turbine was stopped. A nacelle anemometer sits behind the rotor and its calibration assumes the rotor is turning, so exactly when the reading matters most it is least reliable. Phase 2 should reclassify these using the median wind speed of the other turbines and report how much the count moves. |
| **May change** | Yes, on both counts. |

### P-07 Reference period selection

| | |
|---|---|
| **Proposed** | Train on 2014, test on 2015. |
| **Evidence** | Coverage is 99.99% in both years and the split is close to 50/50, giving a full seasonal cycle on each side. A chronological split is required because ten-minute SCADA records are heavily autocorrelated; a random split would put near-identical conditions in both sets and flatter the model. |
| **Alternative** | A 70/30 split. Rejected: it would break the seasonal cycle and make the test period seasonally unbalanced. |
| **Limitation** | Only one split is tested, so the result depends on 2014 and 2015 being comparable wind years. That has not been checked, and reanalysis data is available to check it. |
| **May change** | Yes, after comparing the two years' wind resource. |

### P-08 Healthy-reference filtering

| | |
|---|---|
| **Proposed** | Build the expected-power reference from records that are: not excluded by P-03 to P-05, producing above zero, wind between cut-in and 25 m/s, pitch within −5° to 95°, temperature above −30 °C, and not inside a stuck-sensor run. |
| **Evidence** | 33 temperature records read −273.2 °C, which is at absolute zero and therefore a fault placeholder, not a measurement. All 33 are on R80721 — the same turbine with the longest data outage. 43 pitch records fall outside the sensible range. |
| **Alternative** | Fitting on everything. Rejected: the reference would absorb degraded and stopped operation as normal, and would then fail to flag it. |
| **Limitation** | **This is the project's deepest weakness.** A reference built from a turbine's own history cannot detect a problem that was present for the whole reference period. With only four turbines, peer comparison is weak, and a site-wide issue would be invisible to both methods. |
| **May change** | Yes. |

### P-09 Air-density treatment

| | |
|---|---|
| **Proposed** | Decide in Phase 2. Whatever is chosen, **the baseline and the challenger must receive the same information.** |
| **Evidence** | SCADA has temperature but **no pressure**. MERRA-2 supplies `surface_pressure`, `temp_2m` and `dens_50m`; ERA5 supplies `surf_pres`, `t_2m` and `dens_100m`. Both are hourly, so aligning them to 10-minute records needs interpolation. Both cover the period comfortably (MERRA-2 1997–2019, ERA5 1999–2020). |
| **Alternative** | Give the ML model temperature while the binned baseline gets only wind speed. **Rejected: that rigs the comparison.** The challenger would win partly because it was handed more information. |
| **Limitation** | Reanalysis density is modelled for a grid cell, not measured at the site. Interpolating hourly values onto 10-minute records adds smoothing. **And this is blocked by P-11:** joining reanalysis to uncorrected SCADA would be an hour out for seven months of every year, which is worse than using no density at all. |
| **May change** | Yes — this is the main open question for Phase 2, and it now depends on P-11. |

### P-10 Minimum persistence for flagging potential underperformance

| | |
|---|---|
| **Proposed** | Require a deviation to persist for at least 6 consecutive valid records (1 hour) before it is flagged. |
| **Evidence** | Single ten-minute deviations are dominated by turbulence and by the wind sensor sitting behind the rotor. Requiring persistence suppresses that noise. The stuck-sensor analysis shows one hour is already long enough to be unusual in this data. |
| **Alternative** | Flagging individual intervals. Rejected: it would produce thousands of flags that no analyst could triage, which is the opposite of the project's point. |
| **Limitation** | **1 hour is a judgement, not a measurement.** It will miss short repeated events. Phase 2 must test 3, 6 and 18 records and report how the flag count and the energy total respond. |
| **May change** | Yes. |

## Part C: open questions that must be settled before Phase 2

0. **Is the P-11 re-timing rule approved?** This now gates everything that joins SCADA to another series, including air density. It must be validated by re-running the seasonal lag test after correction.
1. **Does air density go to both models, or neither?** (P-09) This is the fairness question for the whole comparison.
2. **Were 2014 and 2015 comparable wind years?** Reanalysis can answer this and it decides whether P-07 holds.
3. **What is the empirical cut-in speed?** P-06 currently uses a conservative 4 m/s that was not derived from the data.
4. **Is the R80721 pattern one story or several?** It has the most missing data (1,209 records), the longest outage (132.8 h), and all 33 absolute-zero temperature readings. That may be one instrumentation problem or several unrelated ones.
5. **How is the challenger scored?** Lower error on all data is the wrong target: a model that predicts degraded operation accurately is a *worse* detector. The scoring rule must be agreed before the model is trained, not after.

## Part D: Phase 2 outcomes (30 September 2026)

Phase 1 proposed eleven rules. Phase 2 tested them against the data. This section
records what happened to each. Evidence is in `outputs/tables/`.

### P-11 — APPROVED

All nine validation checks passed. The decisive results: absent intervals went
from 48 to **0**, duplicates from 48 to **0**, and the winter-to-summer lag
difference against ERA5 from **−1 h to 0 h**. Energy was conserved exactly.

`timestamp_corrected_utc` is used for all analysis. All three timestamp columns
are preserved in the processed file, so the correction is reversible.

**A second rule was needed, and it is a judgement.** The wall-clock rule cannot
separate the two copies of a collided spring hour, because both carry the same
text. Each pair is split by continuity of wind speed. The first copy moved in 3
cases and the second in 5, so **file order would have been the wrong rule** — worth
recording, because assuming file order would have been easy and silent. Two of the
eight calls are close (seam gaps 1.33 vs 1.04, and 0.38 vs 0.16 m/s). A wrong call
misplaces six records by an hour within a two-hour window and changes no energy
total.

**Limitation that does not go away:** the mechanism is inferred, not documented by
the data publisher. Nine checks are consistent with it; none proves it.

### P-01 Wind-speed range — APPROVED, and it excludes nothing
0 records fall outside 0–30 m/s (measured range 0.00 to 19.31). Retained as a
guard for future runs, not as a working filter.

### P-02 Power range — APPROVED as revised
0 records above rated +10%; 0 below −50 kW. The 77,431 small-negative records
(18.4%) are kept as **observed auxiliary consumption**, excluded from curve
fitting but never labelled a sensor error. In the loss formula, actual power is
floored at zero so that a turbine drawing power is never counted as producing
negative energy. Verified: the loss never exceeds expected power.

### P-03 Clock-change records — REVISED, superseded by P-11
No longer excluded. All 96 records are retained under corrected unique timestamps.
The Phase 1 proposal to drop them is withdrawn.

### P-04 Frozen wind sensor — APPROVED at 6 records, and it barely matters
Sensitivity at 3, 6 and 12 records moves the total estimate by **0.03 MWh** and the
reference subset by 51 records. Phase 1 flagged this threshold as a judgement
worth testing; the test shows the result does not depend on it. Kept at 6.

### P-05 Missing observations — APPROVED
Excluded from any calculation needing wind or power. Never imputed, never turned
into zero. Verified by two checks. 2.30% of 2015 is unmeasured or unassessable,
and that time is reported as unknown rather than counted as either loss or normal.

### P-06 Zero-power observations — APPROVED as revised
Excluded from the reference subset; retained in full as investigation candidates.
Phase 1's limitation is addressed: the wind judgement now uses **peer-turbine wind
where available** and falls back to the turbine's own sensor only when it must.
Findings resting on the turbine's own sensor are graded **low** confidence,
peer-based ones **medium**. No idle-in-wind finding is graded high.

### P-07 Reference period — APPROVED with a quantified caveat
2014 fits, 2015 is assessed. **The years are not closely comparable:** ERA5 mean
wind +4.53%, mean cubed wind **+13.33%**, and by quarter from −4.2% to +15.3%.

This does not invalidate the split, because the curve is conditioned on wind
speed. It does mean raw annual energy must never be compared between years and
called performance. The residual risk is that 2015 leans harder on the thin
high-wind end of the 2014 curve.

### P-08 Reference-operation filtering — APPROVED, renamed
The term "healthy subset" is dropped throughout, per the Phase 1 review. The data
cannot establish healthy operation. **336,928 records (80.13%)** are
reference-eligible, meaning only that they passed the data-quality rules.

**A rule was added during Phase 2.** Below the operating threshold, expected power
is set to **zero by definition** rather than fitted. Without it, the low-wind bins
are empty — zero-power records are excluded from fitting — and 88% of the year
would have been marked unassessable. That would have been an artefact of the
method, not a fact about the data. The three bin types (`fitted_median`,
`defined_zero_below_threshold`, `unsupported`) are kept distinct in the curve table.

### P-09 Air-density treatment — APPROVED, applied to the baseline
Permitted because P-11 passed. ERA5 `dens_100m`, linearly interpolated from hourly
to ten-minute, mean 1.1952 kg/m³ (range 1.092–1.306).

Formula, following IEC 61400-12-1 as implemented in OpenOA's
`air_density_adjusted_wind_speed`:

    corrected_wind = measured_wind * (density / reference_density) ** (1/3)

Reference density is the mean of the series, which is what OpenOA uses. It keeps
corrected wind on the same scale as measured wind and avoids importing a sea-level
constant unsuited to a 411 m site.

**Three stated limitations:** ERA5 is hourly against ten-minute SCADA; density is
supplied at 100 m against an 80 m hub, with no height adjustment applied; and
interpolation is linear in time, which reads the hour either side of a record.
The last is acceptable here because this is a retrospective study, not a forecast,
and density is an outside weather variable rather than anything derived from
turbine output. Backward-fill was the alternative — it avoids reading ahead but
turns a smooth physical variable into steps.

**If the ML challenger is built, it must receive density too, or the baseline must
lose it.** Giving the model more information and then calling the comparison fair
would be the easiest way to rig it.

### P-10 Persistence — APPROVED at 6 records, with the caveat that it changes attribution only
Sensitivity at 3, 6 and 12 records: below-reference attribution moves from 374 to
223 to 89 MWh, while **the total is unchanged at 672 MWh** in every case.
Persistence decides which records are named as candidates, not how much energy is
counted. Worth stating plainly, because a reader could otherwise take the
attributed figure as the estimate.

### New in Phase 2: the reference quantile is the assumption that matters
Not identified in Phase 1. Moving from the 40th to the 60th percentile changes the
total from **538 to 834 MWh, about ±22%** around the primary 672 MWh. It is the
largest single source of uncertainty in the analysis and there is no measurement
that settles it. The median is retained as the primary specification because it is
the conventional and least arbitrary choice, **not** because of the number it
produces.
